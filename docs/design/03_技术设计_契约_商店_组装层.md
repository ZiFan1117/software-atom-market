# 技术设计：契约、商店、组装层

> 目标：把"代码积木"从口号变成可实现的系统骨架。本文件给**设计语言与最小可行范围（MVP）**，不写具体框架绑定。

## 1. 设计目标与非目标

**目标**
- 砖块内部实现语言不限（Python/JS/Rust/外部 API 均可），对外只暴露统一契约。
- 人与 AI 都只在"意图 + 数据"层操作，不写实现代码。
- 组合在"拼装时"即可校验（类型/契约），而不是"运行时炸"。
- 默认去重：同一能力全球只有一份已验证的砖，生成式重复被生态性消除。

**非目标（YAGNI，先砍掉）**
- 不做可视化拖拽画布（MVP 用文本/JSON 表达接线图即可）。
- 不做去中心化链上信任（先集中一个 Registry）。
- 不解决"本质复杂度"——只承接可模块化的那部分。

## 2. 概念词汇表

| 词 | 含义 |
| --- | --- |
| Brick（砖） | 一个黑盒能力块 = 实现 + 契约 + 测试样例 |
| Contract（契约） | 砖对外的机器可读接口：意图名、说明、输入/输出 schema |
| Wire（接线） | 两块砖之间的一条数据连接：上游输出 → 下游输入 |
| Graph（接线图） | 一组砖 + 一组 Wire，是"拼出来的程序" |
| Store（商店） | 面向拼砖者的可检索砖库（上层=能力原子，下层=原语） |
| Registry（注册表） | 元数据 + 版本 + 签名 + 验证状态的权威源 |
| Runner（运行器） | 解释并执行接线图的沙箱环境 |

## 3. 契约格式（核心：把 stdin/stdout 升级为类型化契约）

UNIX 的教训：任何工具都能咬合（文本流），但类型错误运行时才炸。升级方式：**每个砖在"入口/出口"处声明数据形状**。

用 JSON Schema（与 OpenAPI/MCP 对齐，生态现成）：

```json
{
  "brick": "pdf.extract_tables",
  "version": "1.2.0",
  "intent": "从 PDF 中抽出所有表格",
  "input": {
    "type": "object",
    "properties": {
      "pdf_bytes": { "type": "string", "contentEncoding": "base64", "description": "PDF 文件字节" },
      "page_range": { "type": "array", "items": { "type": "integer" }, "description": "可选，页码范围" }
    },
    "required": ["pdf_bytes"]
  },
  "output": {
    "type": "array",
    "items": {
      "type": "object",
      "properties": {
        "headers": { "type": "array", "items": { "type": "string" } },
        "rows": { "type": "array", "items": { "type": "array", "items": { "type": "string" } } }
      }
    }
  },
  "side_effects": "none",
  "tests": [ { "input": { "pdf_bytes": "..." }, "expect": { "type": "array" } } ]
}
```

**为什么这样设计**
- `intent` 给 AI 检索（语义匹配）与给人可读（理解）用；`input/output` 给拼装期类型校验用。
- `side_effects` 区分两类砖：
  - **纯计算砖**（`none`）：可并行、可重试、无风险，像 Unix filter。
  - **接口砖**（`network`/`file`/`email`…）：碰世界，需要权限声明与沙箱策略。
- `tests`：砖上架前必须过契约测试 → "已验证积木"从机制上成立。

## 4. 商店/注册表 schema（检索层）

每块砖在商店里一条记录（可存 SQLite/Postgres + 向量列）：

```json
{
  "id": "pdf.extract_tables",
  "layer": "capability",          // capability(上层) | primitive(下层)
  "intent": "从 PDF 中抽出所有表格",
  "tags": ["pdf", "table", "parse"],
  "lang": "python",               // 实现语言（对拼砖者透明）
  "version": "1.2.0",
  "verified": true,               // 契约测试通过
  "signature": "sha256:...",      // 实现指纹，防篡改
  "embedding": [0.12, ...],       // intent 的向量，供语义检索
  "deps": [],
  "usage_count": 4821,
  "backed_by": "org/owner"
}
```

检索 = **语义相似（intent embedding）+ 关键词（tags）+ schema 兼容过滤** 三层。Gorilla 的经验：大商店下"检索对"比"生成对"可靠得多。

## 5. 组装层（AI 与人的共同工作台）

拼出来的产物是**接线图**，不是代码。人 + AI 的分工：

```
意图(一句话) ──► ① 意图理解 ──► ② 商店检索 ──► ③ 生成接线图
                                                  │ (每根 Wire 都做 schema 兼容校验)
                                                  ▼
                   ⑥ 回填新大砖(可选) ◄── ⑤ 执行与结果 ◄── ④ 人审/自动校验
```

- **①** 把自然语言意图解析成目标输入/输出形状（必要时 AI 追问澄清）。
- **②** 检索能力原子；找不到 → 下沉到 primitive，让 AI 现场拼一个小接线图，验证后**回填**成新砖。
- **③** 接线图 = 砖引用 + 端口到端口的 Wire。**拼装期静态检查**：上游输出 schema 必须可赋给下游输入（类型不匹配立即报错，而非运行时报错——这是对 UNIX 缺口 1 的修复）。
- **④** 人审：看到的是"砖名 + 意图说明 + 数据流走向"，无需看实现。
- **⑤** Runner 在沙箱执行：纯计算砖随意跑，接口砖按 `side_effects` 申请权限（网络/文件/发信各自授权）。
- **⑥** 高复用的小组合自动沉淀为上层能力砖（商店越用越厚，世界不再重复发明）。

**AI 被约束在哪**：AI 只能产出"砖的选择 + Wire 拓扑 + 参数值"，永远不产出实现代码。这正好实现最初的判断——**AI 搭乐高，不写乐高工厂的注塑机程序**。

## 6. 错误处理与安全

- **拼装期**：schema 不匹配 → 拒绝生成并给出可修建议（"上游输出缺 `headers` 字段"）。
- **运行期**：砖级超时、重试（纯计算砖可幂等重跑）；接口砖调用失败有结构化错误码。
- **安全**：实现只认签名版本；接口砖权限最小化；敏感输入（密钥/文件）不落日志。

## 7. 与现有标准的对齐（避免重新发明轮子）

| 本设计 | 对齐对象 |
| --- | --- |
| 契约 input/output | JSON Schema / OpenAPI |
| 砖 = 可调用工具 | MCP tool / OpenAI function calling schema |
| Runner 接线图 | n8n / Node-RED 的 workflow JSON（同构，只是强类型化） |
| 纯计算砖语义 | Unix filter 的强类型版 |

**差异化卖点**：不是再做一个工作流工具，而是**把粒度问题当一等公民**——货架分"能力层/原语层"，砖必须有 `intent` + `tests` 才能上架。

## 8. MVP 范围（先跑通闭环）

1. 一个 **Contract 校验器**（JSON Schema + 拼装期类型检查）。
2. 一个 **本地 Store**（10~20 块手工封装的能力砖：PDF、CSV、金额换算、天气、发信等）。
3. 一个 **Runner**：读接线图 JSON → 执行 → 出结果。
4. 一个 **LLM 接线工**：自然语言 → 检索 → 生成接线图 → 校验 → 执行（人确认一次）。
5. 验证场景固定一个：**"非程序员用一句话搭出：读表格→换算→汇总→发邮箱"**。

技术选型建议：Python + Pydantic(契约) + SQLite + 任意 LLM API。**先不碰**：可视化画布、分布式、去中心化。
