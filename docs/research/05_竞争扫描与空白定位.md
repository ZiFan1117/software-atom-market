# 竞争扫描与空白定位

> 目的：回答"这世界上有没有人已经在做软件原子市场？"，并据此校准本项目的差异化位置与论文 related work。
> 扫描时间：2026-09（GitHub 检索 + 已知厂商），属快照，引用前请复查。

## 1. 一句话结论

**近似物很多，且遍布六层；但"同款"——同时满足四项要件（见 §3）的开放软件原子市场——没有搜到。**
空白是真的，而且可以精确定义。机会不在"再造一个店"，而在**定义让所有店通用的一层标准**。

## 2. 六层生态速览（谁在做什么）

### A. Agent/工具商店 + 注册表（最接近，但面向开发者，无意图契约）
- **Composio**：AI agent 工具/集成平台，商店 250+ 集成，SDK 接入。粒度=API 集成，契约=参数级。
- **MCP 生态**：官方 Model Context Protocol registry；目录站 mcp.so / Smithery / Glama；GitHub 自建 registry 项目若干。
  - `AgentSafe-AI/tooltrust-directory`：对工具/MCP 做 **A–F 风险分级**（"验证闸门"的雏形，值得盯）。
  - `awesome-mcp-registry`：AI 每周自动筛选的目录。
- Claude Code 插件/skill 市场：多个小项目（atman-marketplace、shipwright 等），颗粒是给 coding agent 的插件/skill。

### B. 技能市场（给 AI 的指令/能力件，非通用软件原子）
- Anthropic Agent Skills（skills 清单格式开源）、OpenClaw、DeepSeek Harness 插件生态（见 `02` §5.1）、distilly/ruflo。
- 共性：消费方是 **coding agent / harness**，不是"解决问题给结果"的普通能力原子；无意图+数据契约、无验证上架闸门。

### C. 工作流/机器人模板市场（组合，但面向流程而非能力原子）
- n8n 模板库、Node-RED flow library、字节 Coze（扣子）bot/插件商店（中文最大的"应用商店"式市场）、Zapier/Make 集成目录。
- 组合介质是"工作流/触发器"，不是类型化数据契约；贡献者以平台方/集成商为主。

### D. 组件注册表（"结构化清单 + 机器消费"前身）
- **shadcn/ui registry**：JSON manifest 声明前端组件，CLI/AI 按清单消费；社区已有 MCP server 去检索它（如 registry-directory-mcp）。
- 印证：清单化 + 机器可消费的路走得通；但只限前端 UI 组件、无意图/验证语义、无能力分层。

### E. 企业 agent 应用商店（封闭生态）
- Salesforce AgentExchange、ServiceNow Store、Microsoft Copilot 连接器/插件市场、Google A2A。
- 特点：店很大，但在各自平台围墙内，契约平台私有。

### F. 研究侧
- Gorilla/APIBench、ToolLLM、τ-bench 等（见 `02` §5）：证明"从大商店里选对工具"是公认难题，且可靠性仍差。
- 学界没有把"能力砖粒度"作为受控自变量的系统研究（见 `04`）。

## 3. 四项要件差距表

| 玩家 | 有"店" | 契约统一 | 粒度=意图的判据 | 验证后上架闸门 | 面向非程序员/AI组装 |
| --- | --- | --- | --- | --- | --- |
| Composio / Coze | 是 | API 参数级 | 无 | 无标准 | 否 |
| MCP registry | 是 | 工具协议级 | 无 | 无 | 否 |
| Claude Skills / DSH 插件 | 是 | 指令件级 | 无 | 无 | 否 |
| tooltrust-directory | 是 | 工具级 | 无 | A–F 分级（雏形） | 否 |
| shadcn registry | 是 | 组件级 | 无 | 无 | 否 |
| 企业商店（AgentExchange 等） | 是 | 平台私有 | 无 | 平台审查 | 平台内 |

**没人在做的四件事**：① 把"最小粒度 = 一次意图"变成**schema 判据与货架分层**；② capability（给所有人）/ primitive（给造砖者）两层货架；③ "测试 → verified → 上架"闸门 + 组合回填闭环；④ 让非程序员 + AI 只操作"意图 + 接线图"。

## 4. 定位校准（对 README/docs 的意义）

- **不重造**的层：宿主/Runner（对齐 DSH 等）、工具协议（对齐 MCP/OpenAPI/JSON Schema）、技能清单格式（对齐 Anthropic Skills/OpenClaw）、组件 registry 消费模式（对齐 shadcn）。
- **本项目的独占层**：把上述件收拢成一个**软件原子标准层**——语言的"意图粒度语义 + 双层货架 + 验证闸门 + 回填闭环 + 人人可用界面"。
- 风险提示：
  - 生态演化极快（DSH 万级插件、MCP 官方 registry、AgentExchange…），标准层若不绑定一个"活宿主"容易被边缘化 → 首个实现应考虑借道现存宿主（如以插件落地）。
  - tooltrust 的 A–F 分级说明"信任"有人先占位 → 验证闸门应主打"功能验证（tests→verified）"而非仅安全分级，错位竞争。

## 5. 对论文 related work 的用法

按"§2 六层"组织相关综述，落到 §3 差距表 = 你的 contribution 的直接证据：
"生态里的每个组件（宿主/协议/目录/信任分级）都已存在，但**没有任何一个系统把它们收拢为以'一次意图'为最小单位、带验证闸门、面向非程序员的两层能力货架**。"
