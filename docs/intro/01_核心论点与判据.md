# 核心论点与判据

## 1. 问题诊断

当前让大模型写软件的主流方式是**逐行生成代码**（LLM 直接吐 .py/.ts/.java）。三个系统性缺陷：

1. **即兴发挥，质量不可控**：同一件事每次生成的结果不一致，bug 随生成规模线性放大，难以审查与维护。
2. **全世界重复造同一段代码**：每次生成都是无记忆的重新发明。软件工程里代码克隆（复制粘贴式复用）本就有大量实证——这等于让"生成"把这个浪费再放大几个数量级。
3. **编程壁垒没有真正消失**：即便 AI 会写码，使用者的价值仍被困在"描述实现细节"，而非"表达意图"。

## 2. 主张

不要 AI"边造积木边写代码"。建立一个**全球共享的能力底座（模块商店）**，把已验证的、可复用的"能力块"沉淀进去：

- **造砖者**（少数程序员/验证者）：把能力封装成黑盒砖块，写契约、做验证、上架。
- **拼砖者**（所有人 + AI）：只做"选砖 + 接线"，不写实现代码。

AI 的角色从"代码生成器"变为"管道胶水 + 接线工"：理解人的意图 → 在商店里检索匹配的砖 → 生成接线图 → 校验 → 执行。

## 3. 关键概念区分（必须先拆清，否则一切讨论打转）

| 概念 | 含义 | 谁关心 |
| --- | --- | --- |
| **实现原子** | 代码层的最小函数（如 SMTP 握手、字符串转大写） | 造砖者内部 |
| **能力原子（Capability Atom）** | 用户**能一句话命名、且不想再拆**的一个动作（如"从这个 PDF 抽出表格"） | 拼砖者 + AI |

"发邮件"内部是一串函数在跑——这不构成反对把"发邮件"当一块砖的理由。**实现层再碎都封装在砖内；商店货架上的砖，粒度由"拼砖者脑子里的命名动作"定义，不由代码行数定义。**

## 4. "最小砖"三判据

一块合格的砖 = 同时满足三条的最小能力单位：

1. **意图可命名**：用户能用单一意图一句话说清"把 X 变成 Y"（对应 unit-task 级、认知组块，见 `02`）。
2. **接口统一且自描述**：接口 = 意图名 + 一句人话说明 + 输入数据 schema + 输出数据 schema；语言无关、可序列化、无隐藏全局状态（对应 Parnas 信息隐藏）。
3. **边界可验证**：黑盒可独立测试，契约有测试样例，上架前过验证。

**判定尺子（口语版）**：再往下拆就得解释"怎么做"了 → 太小，人拼不动；一个砖装下两个意图 → 太大，无法复用。

## 5. 一个必须点破的悖论

直觉上"越原子化（越碎）越自由"，但相反：

- 砖越碎 → 接口数量爆炸 → 统一契约的难度越大；
- 砖越碎 → 商店越大 → AI 检索选错的概率越高（这正是 Gorilla/τ-bench 遇到的现实问题）。

乐高好拼恰恰因为凸点规格统一且砖块数量可控。**组合自由度来自接线图拓扑，不来自砖的碎度。**

## 6. 两层货架模型

- **上层（默认货架）**：能力原子级大砖，人话好懂、数量可控，给所有人 + AI。
- **下层（专家货架）**：实现原语 + 契约测试工具，给造砖者；专家/AI 用下层定制、组合出**新的大砖**，经验证后回填上层。

常规使用只碰上层；需要精细控制时 AI 可替用户"下沉"到下层，但人对实现细节零负担。

## 7. 可辩护论点（对外单句版）

> 在 AI 时代，让"每一个人都能通过代码改变物理世界"的最小可行单元，不是更小的代码函数，而是**与用户一次意图对齐、带统一类型化契约、可独立验证的黑盒能力块**；系统的灵活性由能力块之间的"接线拓扑"提供，可靠性由契约与验证提供，而非由碎片化程度提供。

## 8. 诚实的边界

- 软件有**本质复杂度**（Brooks《No Silver Bullet》），拼砖消解的是"偶然复杂度"。总有一些问题无法靠拼砖解决——论点上要留这个口子，反而更有说服力。
- "非程序员能拼"不等于"非程序员能拼所有东西"。实证（mashup 研究）显示普通用户在"接口对不上、数据要转换"处大面积失败——这正是**类型化契约 + AI 胶水**要补的短板，也是系统存在的理由。
