# 原子公约草案 · 三件套 + 单意图原子性（研究/设计，非现行机器闸）

> 状态：v0.1 草案。把"我们到底在做什么"钉成三件套；其中对齐现有机器闸的是已实现的 `SPEC.md`/校验器；本篇标记了**可演进方向**（v0.3+），不作为当前收录硬闸。

## 0. 一句话

我们不造"又一个包仓库"，而是为一个**新消费者——AI 按意图组合能力**——重焊三件套：
**怎么拆（方法）× 长什么样（标准）× 凭什么信（检测）**。

## 1. 三件套与成熟前身

| # | 件 | 成熟前身 | 我们的定位 / 落点 |
| --- | --- | --- | --- |
| ① | 拆分方法 | SRP、Unix 哲学（直觉版） | **单意图原子性**（最原创，见 §2） |
| ② | 协议标准 | WIT（Component Model）、MCP、JSON-Schema | 在其上补"意图语义层"：`intent` + `description` 四节四图（已实现，`SPEC.md`） |
| ③ | 运行检测 | Design by Contract（DbC）、属性测试 | 契约=断言=测试；结构硬检（现行机器闸）→ 未来属性/集成分层（§4） |

## 2. 单意图原子性（拆分判据，操作化）

> **判据**：一个原子的完整契约（输入→处理→输出→副作用）应能用**一句自然语言**写清，且**不含实现细节**；让一个**没看过实现**的人或模型只凭这句 + 契约就能正确调用它。

- 再小（一个意图要拼多个原子才完成）→ 拆过头，应合并
- 再大（一句话出现多个动词/多个目标，如"读 PDF、转图、再 OCR"）→ 必须拆

当前落地：manifest 的 `intent` 即这句"单意图描述"，`description` 首节 `## 它做什么` 是其展开；机器检查"有这句、无实现细节混入"只能做结构弱检，语义真伪靠作者 + 使用反馈（诚实边界，见 `SPEC.md` §4）。

## 3. 原子公约（契约 Schema 全景；v0.3 扩展区用 § 标注）

每个原子声明（现行必填 `*`，扩展 `+`）：

| 字段 | 现行 | 含义 |
| --- | --- | --- |
| 单意图描述 | `* intent` | 一句话，无实现细节 |
| 输入/输出 Schema | `* input/output` | 数据形状（JSON-Schema 子集） |
| 前置条件 `+` | 拟扩展 | 调用方必须先满足（形状外的跨字段约束） |
| 后置条件 `+` | 拟扩展 | 实现方承诺（输出形状之外的保证） |
| 不变量 `+` | 拟扩展 | 任意成功调用后始终成立的性质 |
| 副作用声明 | `* side_effects` | 权限/网络/成本 |
| 详情（怎么实现/边界/示例/图） | `* description` | 渐进披露 L2，四节四图（机器硬检） |
| 验证用例 | `* tests`（结构）+ `+` 断言 | tests 现状只查结构；断言执行化是 v0.3+（需 Runner） |
| 版本与依赖 | `* version` / `deps` | 语义化版本；原子间依赖 |

**演进原则**：DbC 字段不写成纸面空话——要么能当断言执行，要么不进默认货架。因此 v0.3+ 才启用，且需 Runner 支持。

## 4. 检测分层（避免给所有原子配全量验证）

| 层 | 强度 | 对象 | 现状 |
| --- | --- | --- | --- |
| L0 结构硬检 | 轻 | 每个原子必有：字段 + description 四节四图 | ✅ 已实现（机器闸） |
| L1 契约断言（DbC） | 中 | 前置/后置/不变量运行期断言 | 草案（需 Runner） |
| L2 属性/集成回归 | 重 | 高频、复用广的原子 | 草案 |

## 5. 三个提前想清楚的风险

1. **"一次意念"随模型能力漂移**：同一描述，强模型觉得够原子、弱模型觉得太大 → 判据别靠人感觉，靠**往返测试**（同一契约多模型试调，观察调用成功率，做研究基准，见 `docs/04`）。
2. **检测有成本**：按 §4 分层，不铺满。
3. **副作用要可执行**：别只写"network/email"标签——未来对接沙箱/能力模型把权限声明变运行时强制（对应 `docs/03` Runner 与 `side_effects` 语义）。
