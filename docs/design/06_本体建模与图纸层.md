# 本体建模与图纸层（研究笔记）

> 状态：想法阶段，未落 spec。目的：把"原子市场还要有标准软件工程工件（流程图/依赖图/调用图）+ 学术本体建模"这层思考钉下来，避免和现有契约层混淆。

## 1. 四层拆分（核心，先立边界）

| 层 | 内容 | 例子 | 现有程度 |
| --- | --- | --- | --- |
| L0 契约层 | atom manifest：`intent` + `input`/`output` 形状 + `side_effects`/`tests` | `pdf.extract_tables` | 已实现（v0.1） |
| L1 组装层 | **Atom 之间**的图：依赖（`deps`）+ 数据流（上游 output → 下游 input） | 抽表 → 换算 → 汇总 | 可由 manifest 推导，未形式化 |
| L2 图纸层 | **单个原子内部**"怎么实现"的富化：流程图 / 调用图 / 依赖明细 | 抽表原子的内部流程 | 未实现（`description` 只是 Markdown 文字） |
| L3 实现层 | 真实可执行代码 | 作者仓库 | 不入库（`implementation_ref` 外链） |

**铁律**：函数调用图/流程图属于 L2/L3（单个原子内部实现），L1 只有"原子级依赖"。两者粒度与语义不同——是 docs/intro/01「能力原子 vs 实现原子」区分的延伸。不要把调用图塞进 L1。

## 2. 学术术语对照（防混淆）

| 口语 | 学术叫法 | 备注 |
| --- | --- | --- |
| 给能力/服务建模 | 能力本体 / 服务本体（Capability Ontology；OWL-S / WSMO） | 2000s 老牌；docs/research/02 §6 谱系 |
| 给代码内部结构建模 | 源代码本体（Source-Code Ontology）/ 程序理解本体 | 偏研究、生态散 |
| 流程图/时序/架构图语言 | UML / BPMN / SysML / ISO 42010 | 图形规范，非本体 |
| 图表示本身 | 调用图 CG、控制流图 CFG、依赖图 PDG、数据流图 | 经典程序表示，先于本体 |
| 全部合起来的知识化 | 软件本体 / 代码知识图谱（Code Knowledge Graph, CKG） | 正在升温 |

一句话：**图是实例视图，本体是盖在图上的 schema/公理层**。图没有本体也能画（好看）；有本体才能被机器推理。

## 3. 本体草案（L1 起步，贴我们已有字段）

```
类：Atom ⊑ owl:Thing
    CapabilityAtom ⊑ Atom   (layer=capability)
    PrimitiveAtom   ⊑ Atom   (layer=primitive)
    (值域类型 vocabulary：由 input/output 的 JSON-Schema 形状抽象，见开放问题)

对象属性：
    hasIntent    : Atom → Literal  (一句话)
    hasDetail    : Atom → Literal  (description, Markdown)
    hasTag       : Atom → Literal
    hasInputShape  : Atom → 值域类型
    hasOutputShape : Atom → 值域类型
    dependsOn    : Atom → Atom    (来自 deps；acyclic 约束)
    sideEffects  : Atom → {none, network, file, email, db, process}
    verified     : Atom → boolean (annot: 需 tests 非空)

推导视图（实例化即得图）：
    Atom 依赖图    = dependsOn
    Atom 数据流图  = hasOutputShape ⊓ hasInputShape 匹配出的 Wire 候选
    (L2 图纸不在此层)
```

## 4. L2 图纸字段设想（暂不入 spec，先留档）

```jsonc
{
  "id": "pdf.extract_tables",
  "diagrams": [
    { "kind": "flowchart",  "format": "mermaid", "ref": "https://.../flow.md" },
    { "kind": "callgraph",  "format": "dot",     "ref": "https://.../calls.dot" },
    { "kind": "dependency","format": "mermaid", "ref": "https://.../deps.md" }
  ]
}
```
- `kind`: flowchart / callgraph / dependency / sequence …
- `format`: mermaid / dot / png / svg …（消费端决定渲染）
- 图纸**存作者处**（与实现同仓），store 只收元数据 → 与"只收 manifest"一致，渐进披露的更深一层（read 到 description 后可再按 `ref` 取图纸）。
- 校验规则（若启用）：kind/format 枚举合法、ref 是 URL、非空。

## 5. 对本体的开放性研究问题（可发论文的钩子）

1. 契约(schema)与本体(OWL)如何分层配合——**schema 当语法、本体当语义**？
2. "值域类型"词汇从哪来：自建 / 复用 schema.org + SHACL / JSON-Schema→OWL 映射？这是本体工程与既有 spec 的缝合点。
3. L1 依赖图能否支撑**拼装期的可满足性检查**（类型匹配 + 无环 + 副作用权限），把 docs/design/03 的"拼装期校验"上升为推理。
4. 与 OWL-S/语义服务谱系（docs/research/02 §6）做定量对照：静态契约 + 模型动态匹配 的混合方案仍是空白。

## 6. 建议节奏

- 先别急着上 OWL：把 L1 的 `deps` 语义和"Atom 数据流图"用轻量 RDF/Turtle 或 JSON-Graph 跑通 demo，验证推导有价值后，再上完整本体 + 推理。
- L2 图纸是**展示层/渐进披露**问题，与本体正交，可独立推进、成本低。
