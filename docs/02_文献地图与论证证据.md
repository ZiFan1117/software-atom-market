# 文献地图与论证证据

## 0. 诚实声明（引用前必读）

- **直接结论**：目前**没有一篇**文献能直接回答"最小颗粒度应切到哪一级，才能让 AI 时代人人像搭乐高一样拼软件"。这个确切切分点**是开放的**（对研究者=机会）。
- 本文把证据分成五层，每层都能给出**可信锚点**，合起来支撑"三判据"论点。
- 标注：
  - `[经典]` = 学界公认经典，可按作者+年份+出处引用，风险极低。
  - `[已核验]` = 本次已在 Crossref/全文源确认存在（附 DOI/arXiv id）。
  - `⚠ = 建议引用前二次核验`（凭记忆列出，作者/编号请再确认）。

## 1. 认知层——为什么砖不能太碎

| 文献 | 要点 | 用途 |
| --- | --- | --- |
| Miller, *The Magical Number Seven, Plus or Minus Two* (1956), Psychological Review `[经典]` | 工作记忆约 7 个组块 | 人同时能拼的块数有限→块必须"高信息密度" |
| Cowan (2001), *The magical number 4 in short-term memory*, BBS `[经典]` | 修正为约 4 个组块 | 同上，更保守 |
| Chase & Simon (1973), *Perception in chess*, Cognitive Psychology `[经典]` | 专家拼的不是单子，是记忆里的"块" | 颗粒度必须对齐使用者已有的认知块 |
| Green & Petre (1996), *Usability Analysis of Visual Programming Environments: A Cognitive Dimensions Framework*, JVLC `[经典]` | closeness of mapping（表示离任务多近）、abstraction gradient | 理论框架：颗粒度应贴着"人的任务"，而非实现层 |
| Card, Moran & Newell (1983), *The Psychology of Human-Computer Interaction*, Erlbaum `[经典]` | **unit-task 级**：系统应操作在"一次意图"粒度 | 直接支撑"一次意图 = 一块砖" |

## 2. 分解层——模块化判据是"藏什么"，不是"多小"

| 文献 | 要点 | 用途 |
| --- | --- | --- |
| Parnas (1972), *On the Criteria to Be Used in Decomposing Systems into Modules*, CACM `[经典]` | 模块化判据 = **信息隐藏**，与模块大小无关 | 消解"发邮件 vs 小函数"之争：接口设计决定灵活性 |
| Dijkstra (1972), *The Humble Programmer*, CACM `[经典]` | 人只能掌控少量抽象层次 | 支撑分层封装 |
| Brooks (1986), *No Silver Bullet*, IEEE Computer `[经典]` | 本质复杂度不可被工具/复用消除 | 论点留边界，避免过度承诺 |

## 3. 浪费层——"反复造轮子"的实证（论文引言弹药）

| 文献 | 要点 | 用途 |
| --- | --- | --- |
| Roy & Cordy (2007), *A Survey on Software Clone Detection Research* `[经典]` | 代码克隆（复制粘贴式复用）在真实系统普遍存在 | "重复代码是浪费"有据可依 |
| Cardoen, Mens & Decan, *An Empirical Analysis of Code Clones in GitHub Actions Workflows*, SANER 2026, DOI: 10.1109/SANER67736.2026.00028 `[已核验]` | 11.8 万 workflow：**三分之二含克隆**，多数本可用内建复用机制消除 | "即使有复用机制，人/生态仍默认复制"——正好论证需要更强的默认复用底座 |

**论证链**：克隆实证证明"人类重复造轮子"是系统性问题 → LLM 逐行生成把这种重复放大为**每次全新即兴** → 需要一个**默认去重、按契约复用**的共享底座。

## 4. 终端用户层——"非程序员拼积木"的老实证

| 文献 | 要点 | 用途 |
| --- | --- | --- |
| Lieberman, Paternò, Klann & Wulf (2006), *End-User Development*, Springer `[经典]` | EUD 领域奠基文集 | 定义"非程序员编程"的问题空间 |
| Ko et al. (2011), *The State of the Art in End-User Software Engineering*, ACM Computing Surveys `[经典]` | 综述：非程序员**能拼，但拼不动低层原语** | 反对"越原子越好"的最强综述依据 |
| Wong & Hong (2007), *Making Mashups with Marmite: Towards End-User Programming for the Web*, CHI `[经典]` | 普通人拖拽组合 Web 服务时，卡死在**接口对不上、数据要转换** | "接口异质"是普通人组合失败的主因 → 类型化统一契约的必要性 |
| Cypher et al. (2010), *No Code Required*, Morgan Kaufmann `[经典]`（建议核验出版社） | PBE/EUD 案例集 | 背景参考 |

**关键推论**：2007–2010 的 mashup 研究已证明"给人拼积木"可行但败在接口层；当年缺的正是今天的 **LLM 接口匹配 + 类型化契约**。

## 5. AI 时代层——从"生成"转向"检索 + 组装"

| 文献 | 要点 | 用途 |
| --- | --- | --- |
| Schick et al. (2023), *Toolformer*, arXiv:2302.04761 `[已核验]` | 模型自学"何时调工具" | 工具即积木的开端 |
| Patil et al. (2023), *Gorilla: LLM Connected with Massive APIs*, arXiv:2305.15334 `[已核验]`（Crossref 已确认） | 在 1600+ API 商店中做"选对工具"；建 APIBench 基准 | **模块商店 + 检索**的直接前身 |
| Qin et al. (2023), *ToolLLM*, arXiv:2307.16789 `[已核验，建议核验版本]` | 16000+ 真实 API 的工具组装与执行 | 商店规模上移到万级 |
| Shen et al. (2023), *HuggingGPT*, arXiv:2303.17580 `[已核验]` | 把整个模型/工具库当积木池，LLM 做规划 | "大商店 + LLM 当胶水"的系统范式 |
| Yao et al. (2024), *τ-bench*, arXiv:2406.12045 `⚠ 建议核验` | 真实域 tool-agent 基准：顶级 agent 可靠性仍低 | 证据：**工具又碎又多 + 接口不一致 → AI 也拼不动** |

**你的论点的最新语境**：2023 起工业界已出现统一工具契约运动（MCP/Anthropic，2024；以及 OpenAPI/JSON Schema 作为描述语言）。学术界缺的是**对"砖块粒度与契约设计如何影响人机协作组装成功率"的严格研究**。

## 6. 知识谱系（写"动机史"的最佳素材）

```
2000s  语义 Web 服务：OWL-S / WSMO（用本体给接口机器可读语义，想自动组合服务）
   └─ 失败主因：本体标注成本高、无统一执行体
2007+  mashup 时代：Yahoo! Pipes、Marmite（想让人拖拽拼 Web 服务）
   └─ 失败主因：接口异质、数据转换难（普通用户卡死）
2023+  LLM function calling / Toolformer / Gorilla / MCP
   └─ LLM 恰好补上"接口匹配器"这块缺失的胶水
```

**对你（本体/知识工程背景）的独特价值**：老"语义服务组合"试图用**静态本体**让机器理解接口；新方案用**模型语义**做匹配。研究"静态契约 schema + 模型动态匹配"的**混合粒度设计**，是本体与 LLM 交叉的处女地。

## 7. 空白清单（写完论文引言后能认领的部分）

1. 不存在"能力砖粒度"的形式化度量（UNIX 的 do-one-thing-well 是口号，非公式）。
2. 不存在"粒度 × 人群 × AI 拼装成功率"的对照实验。
3. 不存在"契约类型化程度 × 非程序员完成率"的系统测量。
4. 语义 Web 服务（本体标注）与 LLM（语义匹配）两种"接口理解"方案的定量对比仍缺。
